# ex14 · 팩토리 메서드 패턴 — 몬스터 소환 연습 해설

> 부모는 **공통 흐름**을 쥐고, **무엇을 만들지는 자식**이 정한다.
> 이 한 줄을 `step1 → step4`로 손으로 발견해 가는 연습이다.

---

## 발견의 순서

```
공통 분모를 찾는다  →  부모가 흐름을 쥔다  →  무엇을 만들지는 자식이 정한다  →  열려있음을 증명한다
   step1                  step2 (함정)            step3 (완성)                    step4
```

각 step은 **일단 실행된다.** 먼저 돌려서 "어? 이상한데?"를 눈으로 본 다음, TODO를 채워 다음 step으로 넘어간다.

---

## step1 — 중복이 흩어져 있다

`SlimeSpawner`와 `GoblinSpawner`가 **똑같은 소환 흐름을 복붙**하고 있다. 차이는 `new Slime()` / `new Goblin()` 딱 한 줄.

```java
class SlimeSpawner {
    public Monster 소환() {
        System.out.println("던전의 문이 열린다.");   // ┐
        Monster monster = new Slime();               // │ 이 흐름이
        System.out.println("몬스터가 등장한다!");      // ┘ GoblinSpawner에도 그대로 복사됨
        return monster;
    }
}
```

**학생이 할 일**: `Orc`·`OrcSpawner`를 복붙으로 추가한다.

**깨닫는 것**: 소환 흐름을 세 번째로 복사하게 된다. 소환 대사 하나만 바꾸려 해도 **세 군데**를 고쳐야 한다. → 공통 흐름이 흩어져 있는 게 문제다.

---

## step2 — 부모가 생성까지 쥐었다 (함정)

중복이 싫어서 소환 흐름을 부모 `MonsterSpawner`로 끌어올렸다. 흐름은 한 곳으로 모였다 — **좋아 보인다.** 그런데 "무엇을 만들지"까지 부모가 못박아 버렸다.

```java
class MonsterSpawner {
    public Monster 소환() {
        System.out.println("던전의 문이 열린다.");
        Monster monster = new Slime();   // ← 부모가 슬라임으로 못박음. 자식이 못 바꾼다!
        System.out.println("몬스터가 등장한다!");
        return monster;
    }
}
class GoblinSpawner extends MonsterSpawner { }  // 소환()을 물려받지만... 고블린은 어디서?
```

### 실행 출력 — 함정이 눈에 보인다

```
던전의 문이 열린다.
몬스터가 등장한다!
슬라임: 몸통박치기! (3 damage)
----------------------------
던전의 문이 열린다.
몬스터가 등장한다!
슬라임: 몸통박치기! (3 damage)   ← GoblinSpawner인데 슬라임이 나온다!
```

**학생이 할 일**: 고블린을 내려 시도해 보고 **막히는 것**을 확인한다.
- 시도 1) 부모 소환()을 고블린용으로 복사? → **step1로 되돌아간다** (중복 부활)
- 시도 2) 부모에 `if(고블린이면 new Goblin)`? → 새 몬스터마다 **부모를 또 고친다**

**깨닫는 것**: 흐름을 부모로 모은 건 옳았다. 하지만 **무엇을 만들지까지 부모가 쥐면 자식이 못 바꾼다.**
→ 흐름은 부모에 두되, "무엇을 만들지" 그 한 점만 자식에게 넘길 방법이 필요하다.

---

## step3 — 통로로 자식에게 넘긴다 (완성 · 팩토리 메서드)

부모는 `abstract`, "무엇을 만들지"는 **몸통 없는 통로**(`추상 메서드`)로 뚫어 둔다. 부모 `소환()`은 그 통로를 부를 뿐, **무엇이 만들어지는지 모른다.**

```java
abstract class MonsterSpawner {
    protected abstract Monster 생성();          // ← 이것이 팩토리 메서드 (통로)

    public Monster 소환() {                      // ← 공통 흐름은 부모가 고정
        System.out.println("던전의 문이 열린다.");
        Monster monster = 생성();                // ← 자식이 채운 생성()이 불린다 (동적바인딩)
        System.out.println("몬스터가 등장한다!");
        return monster;
    }
}
class GoblinSpawner extends MonsterSpawner {
    protected Monster 생성() { return new Goblin(); }   // ← 자식은 "무엇을" 만 정한다
}
```

**학생이 할 일**: 각 자식의 `생성()` 빈칸 **한 줄**을 채운다.

**깨닫는 것**: step2에서 슬라임이 나오던 `GoblinSpawner`가 이제 **진짜 고블린**으로 공격한다.
자기가 만든 함정을 자기 손으로 풀었다. → **부모는 흐름만, 자식은 무엇을 만들지만.** 이게 팩토리 메서드다.

---

## step4 — 열려있음을 0줄로 증명한다

팩토리 메서드는 완성됐다. 이제 진짜 보상을 손으로 확인한다.

**학생이 할 일**: `Orc`·`OrcSpawner`를 추가한다. **단, 부모 `MonsterSpawner`는 열어보지도 않는다.**

```java
class OrcSpawner extends MonsterSpawner {
    protected Monster 생성() { return new Orc(); }   // 클래스 두 개만 추가하면 끝
}
```

**깨닫는 것**:

| | 몬스터 하나 추가하려면 |
|---|---|
| **step1** | 소환 흐름을 통째로 복사 (여러 곳 수정) |
| **step4** | 부모 수정 **0줄**, 클래스 두 개만 추가 |

이 차이가 팩토리 메서드의 보상이다.

---

## 한 장 요약

| step | 상태 | 부모가 쥔 것 | 자식이 정하는 것 | 실행이 말하는 것 |
|------|------|-------------|-----------------|-----------------|
| 1 | 중복이 흩어짐 | — (스포너마다 흐름 복붙) | — | 흐름을 세 번 복사 |
| 2 | 부모가 생성까지 쥠 (함정) | 흐름 **+ 무엇을 만들지** | 아무것도 못 바꿈 | 고블린인데 슬라임 |
| 3 | 통로로 넘김 (완성) | 흐름 | **무엇을 만들지** | 고블린이 고블린으로 |
| 4 | 열려있음 증명 | 흐름 (불변) | 무엇을 만들지 | 부모 0줄 수정으로 확장 |

> **핵심 문장**: "부모가 공통 흐름을 정하고, 무엇을 만들지는 서브클래스가 정한다."

- `step4` : `Orc`·`OrcSpawner` 추가 후 실행.
